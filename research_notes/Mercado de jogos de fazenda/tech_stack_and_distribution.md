## 1. Engine/framework comparison for a web-first 3D game that also ships to iOS/Android/Windows

### Takeaway
As of Nov 2026 the web-native JS/TS engines (Three.js, Babylon.js, PlayCanvas) are the only 3D options that comfortably meet the strictest portal payload targets (Poki ~5–8 MB initial) and that Poki explicitly calls "purpose built for web"; Unity 6 now officially supports mobile browsers and WebGPU but Poki says its "web export needs work", Godot 4 web export still has recurring iOS Safari crash/memory reports, and Unreal has no official web target. WebGPU is on by default in Chrome/Edge, Safari 26 and Firefox (Windows + Apple-silicon macOS), but not yet universal on Android Firefox/Linux/older devices, so a WebGL2 fallback remains mandatory.

### Cited Findings

**WebGL2 vs WebGPU browser status (2025–2026)**
- web.dev (Google) published "WebGPU is now supported in major browsers": Chrome/Edge desktop since v113 (2023); Chrome for Android since v121 on Android 12+ with Qualcomm/ARM GPUs; Firefox on Windows since v141 and on macOS Tahoe 26 (ARM64) since v145; Safari 26 (macOS, iOS, iPadOS, visionOS; announced WWDC June 2025, shipped autumn 2025). Firefox on Linux, Android and Intel Macs was "in progress". [P] — [web.dev](https://web.dev/blog/webgpu-supported-major-browsers)
- Global WebGPU coverage estimates for 2026 conflict: ~76% (citing caniuse) vs. "low-to-mid 80s"; one source says Mozilla targets Firefox-Android WebGPU for late 2026. All unverified secondary figures. [S] — [enterno.io](https://enterno.io/en/s/research-webgpu-adoption-browsers-2026); [webo360solutions](https://webo360solutions.com/blog/webgpu-browser-support)
- Unity itself warns that not all devices reporting WebGPU support deliver consistent experiences (hence keep a WebGL fallback). [P] — [Unity blog: web runtime updates](https://unity.com/de/blog/engine-platform/web-runtime-updates-enhance-browser-experience)

**iOS Safari memory / stability limits (applies to every engine, and to WKWebView wrappers)**
- Apple developer forums: the WebKit per-page memory budget cannot be raised by the page; the ceiling varies with device RAM and system load. [P/F] — [Apple Developer Forums 741624](https://developer.apple.com/forums/thread/741624)
- WebKit Bugzilla reports (surfaced: bugs 291677, 300782, 237180, 250558; attribution to individual bugs not verified) describe: the cap being a software policy rather than physical RAM (comparable Android devices load 4–16x more), a page reload during WASM compilation on iOS 18.4, Safari keeping compiled wasm in memory across reloads, and an iOS 15.4-era crash with wasm files over ~9 MB. [F] — [WebKit bug 291677](https://bugs.webkit.org/show_bug.cgi?id=291677); [WebKit bug 300782](https://bugs.webkit.org/show_bug.cgi?id=300782); [WebKit bug 237180](https://bugs.webkit.org/show_bug.cgi?id=237180)
- iOS Safari can drop the WebGL context under memory pressure or after backgrounding; games must handle `webglcontextlost` / `webglcontextrestored`. [S] — [abratabia iOS Safari gotchas](https://abratabia.com/mobile-web-games/ios-safari-gotchas.php)
- Specific numeric limits circulating in blogs (a "hard 2 GB wasm heap cap", a "300–500 MB WebGL heap limit") conflict with each other and are not backed by Apple/WebKit documentation — treat as unverified. [S] — [bugnet.io](https://bugnet.io/blog/how-to-fix-unity-webgl-build-crashing-on-safari-ios)
- Unity forum: iOS WebGL builds crash as memory grows; one user reported 100% crash rate at 1080x1920 output resolution. [F] — [Unity Discussions](https://discussions.unity.com/t/webgl-memory-increment-issue-and-crash-on-ios/894771)
- Babylon.js forum also has an "iOS cannot open app – memory limit" thread (i.e. the limit is engine-agnostic). [F] — [Babylon.js forum](https://forum.babylonjs.com/t/ios-cannot-open-an-app-on-ios-browsers-memory-limit/40698)

### Inferences
- Every instant platform's SDK is JavaScript-first; Unity/Godot support is via "experimental" wrappers (YouTube) or deprecated (Unity→Facebook). A JS/TS engine (Three.js, Babylon.js or PlayCanvas engine-only) removes one translation layer on every target and is the lowest-risk way to reach "every store possible".
- Poki's ~5–8 MB initial-download target is the binding constraint; engines whose empty build is ~1 MB (Defold) or that tree-shake (Three.js, Babylon ES modules, PlayCanvas) fit; Unity/Godot WASM runtimes must be heavily stripped to fit and face the documented iOS Safari memory/context-loss risks.
- For a solo developer working with AI coding assistants, code-centric, text-based projects (Three.js/Babylon.js/PlayCanvas engine in TypeScript; Godot's text scenes/GDScript) are easier for an assistant to read/modify than editor-binary-centric workflows (Unity scenes/prefabs, PlayCanvas cloud Editor). This is an inference; no source compared engines on AI-assisted workflows.
- WebGPU should be treated as a progressive enhancement in 2026: target WebGL2 as baseline (all portals, all WebViews), optionally enable WebGPU where present (Three.js and Babylon both render through either backend).
- Defold is attractive for payload but is primarily 2D-oriented; its fitness for a 3D farm game was not researched.

### Gaps
- No measured, like-for-like initial download sizes/load times for minimal builds of Unity 6 Web, Godot 4.x Web, Babylon.js 9, Three.js, PlayCanvas were retrieved (search budget exhausted). Godot's baseline wasm size was not sourced.
- Unity 6.x WebGPU "production" status and current Pro price need confirmation on Unity's release notes/pricing page (only secondary/snippet evidence).
- Godot licence (MIT, per the brief) and Three.js/Babylon.js licences (MIT / Apache-2.0 per common knowledge) were not re-verified this session.
- React Three Fiber specifics (overhead, suitability for games), Cocos Creator 2026 status and licence text, Defold 3D capability, and asset-pipeline support per engine (glTF, Draco/Meshopt, KTX2/Basis) were not researched. *UNVERIFIED background knowledge:* Three.js, Babylon.js and PlayCanvas all ship glTF 2.0 loaders with Draco, Meshopt and KTX2/Basis support.

## 2. Wrapping a web game for stores (Capacitor / Cordova / Tauri / Electron / TWA / PWABuilder)

### Takeaway
Wrapping is viable on all four stores, with different mechanics: Google Play accepts TWAs (Bubblewrap) with Play Billing via the Digital Goods API, the Microsoft Store accepts PWAs (PWABuilder) with Store billing via the same API pattern and is now free to register, Steam titles are typically Electron + steamworks.js, and Apple accepts WebView (Capacitor) games but rejects thin remote-URL wrappers under guideline 4.2 — so the iOS build should bundle assets locally and add native features (IAP, haptics, notifications, Game Center).

### Cited Findings

**Apple App Store — guideline 4.2 and WebView games**
- Guideline 4.2 (Minimum Functionality) is the usual rejection for wrapped web apps; rejection text typically says the app "isn't sufficiently different from browsing the web"; reviewers ask whether the app offers something you couldn't get by opening the site in Safari. [S] — [MobiLoud](https://www.mobiloud.com/blog/app-store-review-guidelines-webview-wrapper); [Capgo](https://capgo.app/blog/app-store-rejection/)
- Practitioner guidance: Apple and Google do accept WebView-based games built with HTML5/JS/WebGL in Capacitor-like wrappers; offline functionality, native API integration (haptics, push, Game Center) and polished native presentation help; a game that just loads a remote URL with no native features may be rejected. [S] — [abratabia: app store submission](https://abratabia.com/native-wrappers/app-store-submission.php)
- PWABuilder has documented enabling StoreKit in-app purchases for PWAs packaged for iOS. [P] — [PWABuilder blog](https://blog.pwabuilder.com/posts/you-won't-believe-how-we-enabled-in-app-purchases-for-pwas-on-ios)

**Capacitor IAP plugins**
- `@revenuecat/purchases-capacitor` is an officially supported RevenueCat plugin (transferred from the community) covering iOS and Android; a skills guide lists it and Capawesome Purchases as the main options and says both require Capacitor 8+. [S] — [RevenueCat purchases-capacitor (index)](https://awesome.ecosyste.ms/projects/github.com%2FRevenueCat%2Fpurchases-capacitor); [Capawesome skills guide](https://skills.sh/capawesome-team/skills/capacitor-in-app-purchases)

**Google Play — Trusted Web Activity (Bubblewrap)**
- Play Billing in a TWA uses two web APIs: the Digital Goods API (SKU details, purchases/entitlements) and the Payment Request API (purchase flow with Google Play as payment method). Requirements: Bubblewrap project with working Digital Asset Links, app listed on Play with a build on a test track, HTTPS. Supported only by Chrome (101+) when the PWA runs in a TWA; feature-detect `window.getDigitalGoodsService`. Bubblewrap outputs AAB/APK for Play Console. [P] — [Chrome for Developers: Play Billing in TWA](https://developer.chrome.com/docs/android/trusted-web-activity/play-billing); [chromeos.dev: PWA Play Billing](https://chromeos.dev/en/publish/pwa-play-billing)

**Microsoft Store — PWA packaging, fees, own commerce**
- A PWA listed in the Microsoft Store can sell in-app products and subscriptions with the Digital Goods API + Payment Request API; the Microsoft billing method is available only when the PWA is installed from the Microsoft Store on Windows; item IDs are created in Partner Center; testing needs Edge ≥ 134.0.3124.51. [P] — [Microsoft Learn: Digital Goods API](https://learn.microsoft.com/en-us/microsoft-edge/progressive-web-apps-chromium/how-to/digital-goods-api)
- Registration: free for individual developers (global, ~200 markets) per Microsoft's 10 Sep 2025 post (previously ~US$19); company accounts also free with faster onboarding per the 7 May 2026 post (previously US$99 one-time). [P] — [Windows Developer Blog 2025-09-10](https://blogs.windows.com/windowsdeveloper/2025/09/10/free-developer-registration-for-individual-developers-on-microsoft-store/); [Windows Developer Blog 2026-05-07](https://blogs.windows.com/windowsdeveloper/2026/05/07/publish-to-microsoft-store-as-a-company-now-with-free-registration-and-faster-onboarding/)
- Revenue share: using Microsoft's commerce platform costs 12% for games and 15% for apps; the "bring your own commerce, keep 100%" option applies to **non-gaming apps only** — no source says games may use their own commerce. [P] — [Microsoft Learn: Get started with the Microsoft Store FAQ](https://learn.microsoft.com/en-my/windows/apps/publish/faq/get-started-with-the-microsoft-store)

**Steam — Electron vs Tauri**
- Electron bundles Chromium + Node (consistent rendering); Tauri uses the system webview, so a WebGL game must be tested on three engines (WebView2 on Windows, WKWebView on macOS, webkit2gtk on Linux). [S] — [summerengine: three.js game on Steam](https://www.summerengine.com/make-great-games/threejs-game-on-steam)
- `steamworks.js` is a Node binding (achievements, cloud saves, overlay); the overlay is enabled with `electronEnableSteamOverlay()`; overlay support has had platform problems (originally Windows-only) and can go stale if the game doesn't redraw constantly. `steamworks-ffi-node` is an alternative. Tauri has no built-in Steamworks support (needs Rust bindings + commands). [P/S/F] — [steamworks.js on npm](https://www.npmjs.com/package/steamworks.js); [electron-steam-notes](https://github.com/JamesMoulang/electron-steam-notes); [dev.to: steamworks-ffi-node](https://dev.to/arty_prof/steamworks-ffi-node-a-steamworks-sdk-library-for-javascript-game-frameworks-15h1); [GDevelop forum: Tauri + Steam](https://forum.gdevelop.io/t/implementing-steam-achievements-with-tauri/73202)
- An HTML5 game (Drawize) shipped on Steam with Electron + Greenworks and reported overlay-related crashes. [S] — [Drawize blog](https://www.drawize.com/blog/tech-how-to-release-html5-game-on-steam)
- Steam Direct fee: US$100 per game, returned after US$1,000 in (adjusted gross) revenue. [S] — [Choost Games guide](https://choostgames.com/blog/how-to-publish-a-game-on-steam/)

### Inferences
- A single web build can be wrapped four ways: Capacitor (iOS, and optionally Android for native ad/IAP SDK access), TWA or Capacitor (Android), PWABuilder/MSIX (Microsoft Store), Electron (Steam). The Digital Goods API gives a near-identical JS purchase code path for Google Play (TWA) and the Microsoft Store (PWA).
- TWA runs in the user's Chrome (good WebGL performance, auto-updating engine) but cannot embed native ad SDKs; if mobile ad mediation (AdMob etc.) is the main revenue source on Android, Capacitor (WebView + native plugins) is the more practical wrapper. This trade-off was not sourced directly.
- Because Microsoft does not let games bypass its commerce, IAP in a Store-distributed game must use Store add-ons (12% fee) — still the cheapest of the major stores.
- For Steam, Electron is the lower-risk wrapper for a WebGL game (single rendering engine, existing Steamworks bindings).

### Gaps
- No source retrieved on AdMob/other ad plugins for Capacitor/Cordova, or on Google's policy for ads inside WebViews (search budget exhausted). *UNVERIFIED background knowledge:* community AdMob plugins for Capacitor exist, and Google provides a "WebView API for Ads" for registering WebViews with the Mobile Ads SDK.
- No source on WKWebView WebGL/WebGPU performance versus Safari, nor on Cordova status in 2026.
- Apple's own guideline text (4.2, 4.7 for HTML5 mini-games) was not opened; all 4.2 evidence is practitioner blogs.
- Steam's 30% commission and Steamworks microtransaction API requirements for F2P games were not sourced this session.
- Microsoft Store content/certification policies specific to games and MSIX packaging details were not retrieved.

## 3. Requirements and status of each instant platform in 2026

### Takeaway
The instant-platform landscape shifted in 2026: Facebook is forcing all Instant Games onto "Network Enabled Zero Permissions" (deadline 31 Aug 2026), sunsetting classic Web/Canvas games and phasing out banner ads; YouTube Playables is still gated early access with ads-only monetization and a revenue-share pilot; Poki and CrazyGames remain the open-submission (curated) web portals with the tightest (Poki ~5–8 MB) and loosest (CrazyGames 50 MB) initial-size targets; Discord Activities are open to all developers with SKU-based IAP.

### Cited Findings

**YouTube Playables**
- Access: "Developer access for Playables is in an early access stage"; interested developers fill out the Playables interest form; resources/Developer Portal access are granted after onboarding. ## 4. Store costs, commissions and registration requirements (incl. a Brazilian individual or company)

### Takeaway
2026 is a year of falling but region-fragmented store fees: Google settled with Epic (4 Mar 2026) and is moving to a ~20% IAP service fee plus a separate ~5% billing fee, rolled out by region with "rest of world" (which would include Brazil) due by 30 Sep 2027; Apple currently collects no commission on US external-link purchases while the Supreme Court reviews the case; the Microsoft Store is now free to join and charges 12% on games; Epic charges 0% on the first US$1M per app per year. For a new *personal* Google Play account the 12-testers/14-days closed test still applies.

## 5. Multiplayer architecture and backend options

### Takeaway
For a browser-first farm game the practical 2026 shortlist of sourced options is Colyseus (MIT, Node/TypeScript, self-host or Colyseus Cloud from US$15/month), Nakama (Apache-2.0, self-host; managed Heroic Cloud is priced for funded studios), Cloudflare Durable Objects (usage-based, WebSocket hibernation makes idle connections cheap), SpacetimeDB Maincloud (free tier + US$25/month Pro) and Photon (CCU-priced, 100 CCU free for Fusion/Quantum); Hathora shut down on 5 May 2026, underlining vendor risk for small hosted providers. Pricing for PlayFab, Firebase, Supabase, Rivet, UGS and EOS could not be researched.

### Cited Findings
- **Colyseus**: open-source framework, MIT-licensed, free to self-host with no restrictions; Colyseus Cloud managed hosting starts at US$15/month (managed SSL included; subscription billing with upfront provisioning and proration; a third-party comparison says 32 locations and no CCU limits). A low-authority blog reports version 0.18 shipped 20 Aug 2026 (unverified). [P/S] — [Colyseus pricing](https://colyseus.io/pricing); [Colyseus Cloud pricing & billing](https://docs.colyseus.io/cloud/pricing-billing); [comparegamebackends](https://comparegamebackends.netlify.app/backends/colyseus); [tech-insider](https://tech-insider.org/colyseus-cloud-setup-2026/)
- **Nakama / Heroic Cloud**: Nakama is Apache-2.0 and free to self-host (enterprise clustering needs a commercial licence). Heroic Cloud pricing snapshots (Oct 2026): Nakama on Heroic Cloud "custom pricing"; the cheapest listed plan is Satori (LiveOps) at US$600/month; sources conflict on whether pricing scales with CPU (no DAU/MAU/CCU limits) or with DAU tiers. [P/S] — [Heroic Labs pricing](https://heroiclabs.com/pricing); [supercraft: Nakama self-hosted vs Heroic Cloud](https://crux.supercraft.host/blog/nakama-open-source-vs-managed-backend/); [apis.io plans snapshot](https://apis.io/plans/heroiclabs/heroiclabs-plans-pricing/)

Third-party trackers (checked Oct 2026): Fusion/Quantum 500 CCU = US$125/app/month; Realtime 500 CCU = US$95/app/month. Server/dedicated mode additionally requires paying for headless server compute. The pricing page says Durable Objects require the Workers Paid plan, while another Cloudflare docs page says SQLite-backed Durable Objects are available on the Workers Free plan with limits (conflict — check live docs); SQLite storage billing began Jan 2026 per an aggregator. ### Inferences
- **Architecture fit**: a farm game's core loop (plant/harvest timers, inventory, premium currency) is naturally *server-authoritative request/response* with asynchronous social features (visit, help, trade, co-op orders); only an optional "shared farm, 2–8 players" mode needs a real-time room. That maps well to (a) a stateful room server (Colyseus room or one Durable Object per farm) for co-op presence plus (b) a transactional database for the economy. A persistent shared world (MMO-style) multiplies cost and complexity and is not needed for the genre's proven loops.
- **Transport**: browsers (and all portal iframes/WebViews) reliably support WebSocket; all sourced options here (Colyseus, Nakama, Durable Objects, SpacetimeDB, Photon's JS SDK) work over WebSocket. WebTransport/WebRTC are unnecessary for a low-tick farm sim.
- **Anti-cheat for premium currency**: wallet changes should occur only in server code after server-side receipt validation (Play Billing, StoreKit, Microsoft Store, Discord entitlements, Stars). Client-authoritative stores (plain Firestore writes, Photon relay without server plugins) are unsuitable for the wallet unless combined with server functions.
- **Rough cost per 1,000 CCU (derived, not quoted)**: Photon Fusion public cloud is ≈US$0.25/CCU/month at the 500-CCU tier (US$125), implying roughly US$250+/month for 1,000 CCU; a self-hosted Colyseus/Nakama process on one or two small VMs typically handles 1,000 low-tick WebSocket clients for tens of dollars per month (not sourced — depends on tick rate and state size); Durable Objects with hibernation bill mostly per message, so a farm game sending few messages per minute should cost single- to low-double-digit dollars per 1,000 CCU (not sourced; must be modelled against the pricing page).
- **Vendor risk**: Hathora (and reportedly Unity Multiplay) shutting down in 2026 argues for open-source servers you can self-host (Colyseus MIT, Nakama Apache-2.0) or hyperscale primitives (Cloudflare) over small proprietary hosts.
- Colyseus is TypeScript end-to-end, which pairs with a JS/TS web engine and with AI-assisted development (shared types between client and server).

### Gaps
- Not researched (search budget exhausted): PlayFab pricing/free tier, Firebase/Firestore pricing, Supabase (Realtime) pricing and connection limits, Rivet pricing/licence, Unity Gaming Services pricing, Epic Online Services (web support), Photon's WebGL/WebSocket specifics, Colyseus WebTransport support, SpacetimeDB licence (BSL status) and TypeScript-module support.
- No sourced benchmark of hosting cost per 1,000 CCU for any option; the figures in Inferences are rough derivations.
- Cross-platform identity (guest → linked Google/Apple/Facebook/Discord account, account merge) capabilities per backend were not researched. *UNVERIFIED background knowledge:* Nakama, PlayFab and Firebase Auth support device/anonymous accounts that can later be linked to social providers; Colyseus ships an auth module; CrazyGames and Discord provide their own user tokens that must be mapped to the game's account system.

## 6. Cross-platform ads and payments integration

### Takeaway
Each surface dictates its own ad SDK and payment rail, so the game needs a thin "platform adapter" layer and a server-side wallet: portals (Poki, CrazyGames) and instant platforms (YouTube, Facebook) mandate their own ad SDKs; purchases must use Play Billing (TWA/Capacitor), StoreKit, Microsoft Store add-ons, Discord SKUs or Telegram Stars on those surfaces, while the open web (own site) is the only place a free choice of payment provider exists. Most of this question (ad-network terms, merchant-of-record providers, Pix, Apple's cross-platform currency rule) could not be researched before the search budget ran out.

### Cited Findings
- **Poki**: only Poki's ad SDK/ad system is allowed; third-party tracking tools require prior written consent. [P] — [Poki requirements](https://sdk.poki.com/requirements)
- **CrazyGames**: only ads served through the CrazyGames SDK are allowed; the SDK also handles in-game purchases and user accounts; revenue share begins at Full Launch. [P] — [CrazyGames requirements intro](https://docs.crazygames.com/requirements/intro/); [CrazyGames SDK intro](https://docs.crazygames.com/sdk/intro/)
- **YouTube Playables**: ads (pre-roll, interstitial, rewarded) are served by YouTube through the Playables SDK; revenue sharing is a pilot; no IAP documented. [P] — [Playables monetization](https://developers.google.com/youtube/gaming/playables/reference/monetization)
- **Facebook Instant Games**: ads through `FBInstant` rewarded/interstitial APIs (banner being deprecated by 31 Mar 2027); IAP on iOS/Android/web after Meta approval, with iOS purchases going through Apple's billing. [P] — [Meta changelog](https://developers.facebook.com/documentation/games/whats-new/changelog/); [Meta IAP docs](https://developers.facebook.com/documentation/games/monetize/in-app-purchases.md)
- **Discord**: purchases via Discord SKUs (`getSkus`/`startPurchase`), entitlements verified server-side. [P] — [Discord docs](https://docs.discord.com/developers/monetization/implementing-iap-for-activities)
- **Telegram**: digital goods are paid in Stars; Stars convert to TON via Fragment or ad credit. [S] — [The Block](https://www.theblock.co/post/298954/telegram-launches-digital-mini-app-payment-system-telegram-stars)
- **Google Play (TWA)**: Digital Goods API + Payment Request API with Play Billing. **Microsoft Store (PWA)**: Digital Goods API + Payment Request API with Microsoft Store billing. [P] — [Chrome for Developers](https://developer.chrome.com/docs/android/trusted-web-activity/play-billing); [Microsoft Learn](https://learn.microsoft.com/en-us/microsoft-edge/progressive-web-apps-chromium/how-to/digital-goods-api)
- **iOS/Android native wrappers**: RevenueCat's official Capacitor plugin wraps StoreKit and Play Billing behind one API. [S] — [RevenueCat purchases-capacitor (index)](https://awesome.ecosyste.ms/projects/github.com%2FRevenueCat%2Fpurchases-capacitor)
- **Web shop option**: Epic Web Shops (0% on first US$1M/app/year, then 12%) is positioned as a direct-to-player store for mobile and PC games. [P] — [Epic Web Shops](https://store.epicgames.com/distribution/web-shops)
- **Link-out economics**: Apple currently takes 0% on US external-link purchases (subject to pending litigation); Google permits external payment links under the settlement but still charges a service fee. [S] — [MacDailyNews 2026-08-14](https://macdailynews.com/2026/08/14/u-s-supreme-court-clears-path-for-app-store-commission-showdown-as-apple-must-defend-its-rates-in-lower-court/); [iClarified 2026-07-22](https://www.iclarified.com/101291/google-opens-play-store-to-alternative-payments-under-epic-settlement)

### Inferences
- One wallet across platforms requires: a single server-side account ID, a ledger of currency grants keyed by (platform, transaction/receipt ID), server-side receipt validation per platform, and platform-specific SKUs/prices. The client only requests "buy SKU X via the current platform adapter".
- Because portals forbid third-party ad SDKs, ad code must be behind an interface (`showRewarded()`, `showInterstitial()`), with implementations for Poki, CrazyGames, YouTube, Facebook, own-site (a web ads network) and native (mobile mediation via Capacitor plugin).
- Portals/instant platforms may restrict spending or advertising currency bought elsewhere; the safest pattern is that currency bought anywhere is usable everywhere but each surface sells only through its sanctioned rail and never advertises cheaper external prices where steering is prohibited.

### Gaps
- **Not researched (budget exhausted):** Google H5 Games Ads / AdSense for games eligibility and terms; AdMob, Unity LevelPlay, AppLovin MAX in WebView/Capacitor apps; Meta Audience Network terms; Stripe/Xsolla/Paddle as merchant of record; Pix acceptance (Mercado Pago, Stripe, Xsolla) and fees in Brazil; Apple's and Google's rules for currency purchased on other platforms.
- *UNVERIFIED background knowledge (verify before relying on it):*
  - Apple App Store Review Guideline 3.1.3(b) "Multiplatform Services" has allowed apps to let users access consumables acquired on other platforms or the developer's website, provided those items are also available as in-app purchases within the app (see developer.apple.com/app-store/review/guidelines).
  - Google offers "H5 Games Ads" (Ad Placement API, interstitial + rewarded) for HTML5 games on the open web, with gated/approved access.
  - Telegram requires digital goods sold inside Mini Apps to be paid for with Stars.

## 7. 3D art pipeline for a small team

### Takeaway
This question could not be researched before the shared search budget was exhausted; the only sourced inputs are the platform payload targets gathered for question 3 (Poki ~5–8 MB initial, Facebook <5 MB recommended initial / 200 MB total, YouTube Playables <15 MiB recommended / <30 MiB required initial and <250 MiB total, CrazyGames ≤50 MB initial / ≤20 MB for mobile homepage), which define the art budget: a tiny first-load scene and aggressive lazy loading of everything else.

### Cited Findings
- Poki initial-download target ≈5–8 MB. [P] — [Poki requirements](https://sdk.poki.com/requirements); [Poki for Developers](https://developers.poki.com/guide/web-game-engines)
- Facebook Instant Games: recommended initial bundle < 5 MB; hard total limit 200 MB. [P] — [Meta: game performance](https://developers.facebook.com/documentation/games/build/game-performance)
- YouTube Playables: initial bundle < 30 MiB required (< 15 MiB recommended); total < 250 MiB; individual files SHOULD be < 512 KiB per the stability page (i.e. many small, lazily fetched files are preferred). [P] — [Playables stability requirements](https://developers.google.com/youtube/gaming/playables/certification/requirements_stability)
- CrazyGames: initial ≤ 50 MB, total ≤ 250 MB, ≤ 1,500 files; ≤ 20 MB initial for the mobile homepage (third-party). [P/S] — [CrazyGames technical requirements](https://docs.crazygames.com/requirements/technical/); [summerengine](https://www.summerengine.com/make-great-games/publish-an-html5-game)
- iOS Safari memory ceilings are policy-based and lower than comparable Android devices, and WebGL context loss occurs under memory pressure — texture memory is the main risk on iPhones. [P/F] — [Apple Developer Forums 741624](https://developer.apple.com/forums/thread/741624); [abratabia](https://abratabia.com/mobile-web-games/ios-safari-gotchas.php)

### Inferences
- A stylized low-poly look (flat colours/vertex colours or one shared palette texture atlas) is the art direction most compatible with a 5–8 MB first load: geometry compresses well with Meshopt/Draco, and palette-based materials avoid large textures and allow heavy batching/instancing.
- Crops and trees should be GPU-instanced (one draw call per crop type/growth stage) — a farm scene with thousands of identical plants is the textbook instancing case; this is an engineering inference, not sourced.
- YouTube's 512 KiB per-file recommendation and the 1,500-file CrazyGames cap pull in opposite directions; chunking assets into ~0.3–0.5 MB bundles grouped by feature satisfies both.

### Gaps
- **Entire question not researched.** Missing: asset-pack licences, AI 3D generators and their licence terms in 2026, concrete mobile-web performance budgets (draw calls, triangles, texture memory), instancing guidance per engine, compression benchmarks (Draco vs Meshopt, KTX2/Basis UASTC vs ETC1S).
- *UNVERIFIED background knowledge (verify licences on each vendor's site before use):* Kenney, Quaternius and KayKit asset packs have been distributed under CC0 (public domain, commercial use allowed, no attribution); Synty packs are paid under a proprietary EULA (per-seat licence, restrictions on redistribution); Meshy and Tripo have historically licensed free-tier outputs under CC BY 4.0 (attribution, public) and granted private/commercial ownership only on paid plans; Rodin (Hyper3D) terms unknown. Commonly cited mobile-web budgets (≈100–200 draw calls, ≈100–300k visible triangles, compressed GPU textures) are rules of thumb, not verified here.
